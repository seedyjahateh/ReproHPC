# Release and archival reproduction

There is no published release lock or DOI yet. Never replace missing identifiers with plausible-looking values. A reserved Zenodo DOI is not registered until publication; creators and metadata must be confirmed. See [Zenodo's upload and DOI instructions](https://help.zenodo.org/docs/deposit/create-new-upload/).

The [candidate license review](license-review.md) links actual installed notices and binary build configuration, and identifies remaining source-preservation and creator/rights work.

1. Finish every P0 acceptance item and record evidence for the exact candidate. Set final project version and prepare release notes disclosing the supported algorithm, platform, scaling envelope, and absent independent review where applicable.
2. Confirm creator names, affiliations/ORCIDs where available, software MIT, documentation CC BY 4.0, and synthetic data/reference CC0. Audit the actual container's installed dependency notices.
3. Create separate software and demonstration-data draft records. Reserve actual version DOIs. Record concept DOIs separately for discovery; reproduction must use version identifiers. Cross-link software, data, reference, and results with qualified relations.
4. Freeze a clean source commit. Build its OCI image from the platform digest and hashed dependency lock. Convert it once to the canonical SIF; archive these exact SIF bytes. Container rebuilds are not assumed byte-identical.
5. Package source, SIF, data, reference, expected scientific results, parameters, schemas, tool distribution identities, licenses, and all acceptance evidence. Generate external SHA-256 files. The release lock schema is `schemas/release.json`; fill its values exclusively from real artifact metadata. Validate it using `scripts/validate_release.py` and the exact-candidate Slurm evidence. Do not hand-edit evidence booleans to bypass failed tests.
6. Upload and preview both records, then publish only after all candidate gates pass. Do not change historical artifact bytes. Corrected bytes require a new immutable record version.
7. Download from public record URLs without authentication into a new cache. Run `prepare`, then `reproduce` in a fresh directory with the archived source and SIF. Repeat on the supported Slurm site. Verify both version DOI landing pages and all file hashes; retain logs and comparison JSON. Update CITATION.cff and the README with actual resolving identifiers.

Because a source archive cannot include its own checksum or a commit that hashes itself, the final release lock is an external release artifact pointing to the frozen source archive/commit. It can be distributed beside the extracted source launcher. Keep the lock and SIF/data/reference/goldens independently archived so reproduction survives an unavailable image registry.

The manual release workflow runs on that frozen source revision and accepts the external lock and acceptance bundle HTTPS URLs and SHA-256 values as inputs. Both are saved under ignored `artifacts/` so retrieving them does not dirty the checkout. The verified acceptance tar.gz contains `slurm-acceptance.json` and its referenced evidence files at relative paths. Keep this evidence external too: a commit cannot include evidence that hashes that same commit. The lock's `environment` must include the exact Java vendor/build, Python, Apptainer and Slurm versions, base digest, all three dependency-lock hashes, installed Python package inventory, and pip/setuptools/wheel pins.

The reviewed Slurm acceptance manifest has an `artifacts` object with `coverage`, `tests`, and `benchmark` entries plus a `slurm_raw` list. Each entry contains a relative `path` and real `sha256`, resolved beneath the manifest directory. The validator reads those files and rejects failed/skipped full-suite tests, insufficient coverage, an unqualified or failing benchmark, missing raw scheduler evidence, and mismatched candidate identities. Obtain entries from actual test/benchmark outputs; do not construct success fixtures for a release. Public DOI checks remain a subsequent required release verification step.

`export` produces a per-run reproducibility package; it does not upload files or mint a DOI. Candidate CI artifacts are temporary and are not a substitute for repository preservation. Do not include access tokens, private usernames/hostnames, absolute operational paths, or raw credentials in public exports.
